## О проекте

`anime-db-plugin-contracts` — пакет PHP-интерфейсов и DTO, определяющий
программный контракт плагинов AnimeDB v2. Репозиторий содержит **только
контракт** (интерфейсы + плоские DTO + правила статического анализа для
проверки соответствия контракту) — никакой реализации плагинов и
никакой бизнес-логики хост-приложения.

Контракт реализуют две независимые стороны:
- **Хост-приложение** (десктопное приложение AnimeDB) — вызывающая
  сторона, использует интерфейсы для обнаружения и вызова плагинов
- **Сами плагины** (официальные и от сообщества) — реализуют интерфейсы
  для конкретных внешних источников метаданных/синхронизации

- **Стек**: PHP 8.x, чистый Composer-пакет (PSR-4 автозагрузка)
- **Статус**: активная разработка
- **Лицензия**: GPLv3
- **Ветка по умолчанию**: `master`

## Ключевые архитектурные принципы

- **Контракт не знает про хост-приложение.** Ни один тип в этом пакете
  не ссылается на ORM-сущности, схему БД или внутреннее устройство
  конкретного хост-приложения. Всё, что плагин отдаёт/принимает — плоские
  DTO этого же пакета (`PluginAnimeData`, `SyncItem`,
  `SearchByPluginCandidate`, `AnimeSearchResult`/`AnimeSearchResultItem`).
  Маппинг DTO во внутреннее представление — ответственность
  хост-приложения, не этого пакета.
- **`ExternalIdResolutionInterface` называет способность, а не категорию
  плагина.** Единственный метод — `resolveExternalId(array $urls): ?string`
  (плагин определяет свой внешний id по списку уже известных ссылок на
  источники). Его наследуют интерфейсы, которым нужна эта способность
  (`FillerInterface`/`SearchByPluginInterface`/`SyncInterface`/
  `EntryWidgetInterface`/`CatalogWidgetInterface`) — по ISP. Не наследует
  `DownloadCandidateSearchInterface`: его `search()` принимает свободный
  текстовый запрос, а не список ссылок, а идентичность кандидата несёт
  `AnimeSearchResultItem::$externalId`. Плагин с манифестным `type: local`
  (реагирует на события каталога, реализует Symfony
  `EventSubscriberInterface`, в сеть не ходит) его тоже не реализует —
  принцип на будущее: каждый тип плагина получает свой role-named
  интерфейс по нужным ему способностям, нет универсальной базы, к которой
  прирастают неуниверсальные допущения. Категория «интеграция» живёт
  только в манифестном `type` (`integration`/`translation`/`local`),
  кодового маркера-категории нет. Перечисление установленных плагинов —
  из манифестов, не из маркер-интерфейса.
- **Сервисы, которые ядро даёт плагинам, тоже часть контракта.**
  `LlmServiceInterface` (доступ к локальной LLM),
  `DownloadServiceInterface` (постановка задачи на скачивание, вместе с
  VO `DownloadSource`/`AnimeId`/`DownloadTaskId` и событием
  `DownloadCompletedEvent`), `PluginDataStoreInterface`
  (read/write собственного payload плагина по `AnimeId`, скоупнутый на
  сам плагин: `pluginId` не в сигнатуре — инстанс, который DI отдаёт
  плагину, уже знает свой) и `CatalogReaderInterface` (read-only проекция
  текущего состояния записи по `AnimeId`, DTO `AnimeView`) — интерфейсы,
  которые реализует хост-приложение, а получает плагин через DI (как и
  преднастроенный PSR-18 HTTP-клиент — тот случай, когда отдельный
  интерфейс в пакете не нужен, достаточно type-hint на
  `Psr\Http\Client\ClientInterface`).
  `PluginDataStoreInterface::write()` — намеренно без `flush()`: это
  выражение намерения «сохрани», а не шаг жизненного цикла ORM — когда и
  как персистить, решает реализация в хост-приложении, не контракт.
- **`CatalogReaderInterface`/`AnimeView` — «на чтение», не путать с
  `PluginAnimeData` — «на запись».** `AnimeView` — плоский иммутабельный
  DTO текущего смёрженного состояния каталога (не Doctrine-сущность и не
  ORM-модель хоста): виджету нужны общие поля записи, а не только свой
  срез, чтобы отрендерить карточку по `AnimeId`; донасыщению после
  закачки — список эпизодов и т.п. Только чтение — мутации своего среза
  плагина и мутации записи целиком идут другими путями, не через этот
  интерфейс. `AnimeView::$externalId` — внешний id **вызывающего плагина**,
  резолвнутый хостом заранее (дешёвый lookup, а не парсинг `$sources` на
  каждый вызов), поэтому одна и та же реализация `CatalogReaderInterface`
  не может быть общей на всех плагинов без слоя, знающего, для какого
  плагина она инжектирована.
- **`EntryWidgetInterface::render()` принимает `AnimeId`, не внешний id
  (breaking change v0.7.0).** До v0.7.0 сигнатура была
  `render(?string $externalId)` — этого больше нет. Многим виджетам
  внешний id не нужен вовсе (например, виджету статуса закачки достаточно
  `AnimeId`, чтобы прочитать свой срез); тому, кому нужен — резолвит сам
  через унаследованный `resolveExternalId()` по `AnimeView::$sources`,
  либо берёт уже резолвнутый `AnimeView::$externalId` — оба пути идут
  через `CatalogReaderInterface`. `CatalogWidgetInterface` (без контекста
  записи) этой правкой не затронут.
- **`Widget\WidgetMetadata` + `metadata(): WidgetMetadata` на обоих
  Widget-интерфейсах (breaking change, minor под 0.x — экосистема виджетов
  пуста).** `name` — стабильный код-идентификатор (шаблон `[a-z0-9-]+`),
  которым хост ключует виджет как `{pluginId}:{name}` (DI-тег/URL/
  `features`); менять после релиза нельзя без миграции. `titleKey`/
  `descriptionKey` — ключи перевода (не готовые строки): хост резолвит их
  своим Translator'ом в домене перевода плагина (домен = id плагина) в
  текущей UI-локали; плагин обязан поставить строки для этих ключей в
  своём `translations/` как минимум для дефолтной локали. `metadata()` —
  static, а не свойство экземпляра или атрибут: хост-`TagPluginServicesPass`
  читает `name` при компиляции DI-контейнера без инстанцирования класса
  виджета, а интерфейс принуждает реализовать метод (обязательно и
  очевидно, в отличие от опционального атрибута). Возвращаемое значение —
  литеральный VO без побочных эффектов: `metadata()` исполняется при
  сборке контейнера на install/activate плагина.
- **`Manifest` `name`/`description` — самодостаточные литералы, НЕ ключи
  перевода (в отличие от `WidgetMetadata.titleKey`/`descriptionKey`).**
  Манифест — самоописательный standalone-дескриптор, потребляемый
  каталог-агностично: сборка реестра маркета (встраивает `name`/`description`
  в `plugins-registry.json` без Translator/locale), UI установки до активации
  плагина (каталог `translations/` ещё не подгружен), `ManifestParser`/
  `ManifestValidator`, заморозка на install. Ключ перевода здесь попал бы в
  реестр и UI буквально. Это тот же инвариант независимости, что и «контракт
  не знает про хост»: манифест не зависит ни от какого каталога переводов.
  Локализуемые строки — только UI-класс (лейблы настроек/OAuth-страниц
  плагина, `WidgetMetadata.titleKey`/`descriptionKey`), которые хост резолвит
  внутри себя с загруженным каталогом. Если позже понадобится многоязычный
  `description` — только инлайновые варианты внутри самого манифеста (верхний
  литерал = дефолт/фолбэк), не внешние ключи.
- **`Background\BackgroundTaskQueueInterface`/`BackgroundTaskHandlerInterface`
  — отложенная работа плагина, дедупликация в обработчике, не в очереди.**
  `submit()` (core-provided, DI, скоупнут на id плагина — как
  `PluginDataStoreInterface`) кладёт задачу; `handle()` (роль плагина) её
  выполняет в фоновом процессе. `submit()` может положить дубль уже
  стоящей задачи, порядок выполнения не гарантирован, одна и та же задача
  может быть выполнена больше одного раза — поэтому `handle()` обязан быть
  идемпотентным и обязан начинать с проверки «нужна ли ещё эта работа»:
  знать это может только тот, кто делает работу, к моменту выполнения
  состояние могло измениться. Метода `isPending()` в контракте нет — это
  была бы половина связки «проверил → положил», а такой связки при дедупе
  в обработчике не существует. `BackgroundTask::$name` задаёт сам плагин,
  чтобы различать свои виды задач в `handle()`; ядро его не интерпретирует,
  маршрутизация идёт по id плагина, а не по этой строке. `BackgroundTask::$payload`
  обязан быть JSON-сериализуемым: задача переживает перезапуск процесса.
  Расписаний, приоритетов, прогресса и отмены в контракте нет — слово
  «планировщик»/scheduler не используется нигде в пакете.
- **`Catalog\AnimeFilesChangedEvent`/`FilesChangeReason`.** Одно событие на
  четыре причины изменения состава/расположения файлов записи
  (`Created`/`FilesAdded`/`PathChanged`/`DownloadFinished`), а не четыре
  события: потребителю во всех случаях делать одно и то же, а пятая причина
  добавляется значением enum без правки всех плагинов. Диспатчится **после**
  того, как изменение уже закоммичено; подписчик вызывается синхронно.
  Рекомендуемый паттерн — подписчик не делает ничего, кроме
  `BackgroundTaskQueueInterface::submit()`, тяжёлая работа — в `handle()`;
  машинной защиты от нарушения этого паттерна нет.
  `Download\DownloadCompletedEvent` не удаляется и не заменяется этим
  событием — разные факты: «задача загрузки завершилась» (привязана к
  `DownloadTaskId`) против «состав файлов записи изменился».
- **Направление зависимости — только в одну сторону.** И хост-приложение,
  и любой плагин зависят от этого пакета. Этот пакет не зависит ни от
  хост-приложения, ни от какого-либо конкретного плагина.
- **PHPStan-правила** — пакет предоставляет набор правил
  (`NoDangerousPrimitivesRule`, `ContractConformanceRule`,
  `NoNetworkAccessInLocalPluginsRule`), проверяющих код плагина на
  соответствие контракту; сам пакет статический анализ кода плагинов не
  запускает. Потребитель подключает их к собственному прогону PHPStan по
  дереву исходников плагина — либо автоматически через
  `phpstan/extension-installer`, либо вручную через `includes:` на
  `extension.neon` пакета в своём `phpstan.neon` (подробности и пример —
  README, раздел «PHPStan-правила»). Так одна и та же логика проверки не
  дублируется в каждом потребителе по отдельности.
- **`Manifest\ManifestParser`/`ManifestValidator`** — тот же аргумент, что
  и у PHPStan-правил, применённый к разбору `manifest.json`: общий
  компонент для CI реестра и клиентского инсталлятора, чтобы трактовка
  формата манифеста не расходилась между потребителями. Валидатор
  возвращает структурированный список ошибок (`field` + `message`), а не
  булев результат — оба потребителя показывают автору плагина осмысленную
  причину отказа.

## Границы

### MUST
- Лицензионная шапка (копирайт + ссылка на GPLv3) — в каждом исходном файле
- Семвер пакета: изменение сигнатуры существующего интерфейса — минимум
  minor-версия, breaking change (удаление метода, несовместимое изменение
  сигнатуры) — major-версия
- Любой новый DTO/интерфейс — плоский, без внешних рантайм-зависимостей
  (Symfony/Doctrine и т.п.)

### MUST NOT
- Не добавлять сюда реализацию конкретных плагинов (Shikimori/MAL/AniDB
  и т.п.) — это отдельные репозитории плагинов, не этот пакет
- Не добавлять зависимость на хост-приложение или на конкретную ORM —
  ломает независимость контракта
- Не смешивать в одном интерфейсе логику разных фич (filler/widget/
  sync/search) — у каждой фичи свой отдельный интерфейс; общая
  способность резолвить внешний id вынесена в отдельный
  `ExternalIdResolutionInterface`, и то не у всех типов плагинов (у
  `local` и у `DownloadCandidateSearchInterface` — нет и его)
- Не превращать manifest `name`/`description` в ключи перевода — манифест
  самодостаточен и читается каталог-агностично (реестр маркета, UI установки,
  валидатор). Локализуемые строки — только UI-класс
  (`WidgetMetadata.titleKey`/`descriptionKey`, лейблы через `translations/`).
  См. принцип про `Manifest` выше
- Не ужесточать `ManifestValidator` до строгой схемы (отвергать любое поле
  манифеста вне фиксированного списка) — схема `manifest.json` намеренно
  расширяется потребителями за пределами этого контракта (реестр маркета,
  тулинг монорепозитория плагинов). См.
  [.claude-docs/gotchas.md](.claude-docs/gotchas.md)

## Ревью PR

- Автоматическое ИИ-ревью каждого PR — `.github/workflows/claude-review.yml`
  (авторизация через секрет репозитория `CLAUDE_CODE_OAUTH_TOKEN` из подписки Max).
  Черновики не ревьюются: прогон стартует на `ready_for_review`, на `opened` не-черновика
  и на `reopened`; повторное ревью — через reopen/ready, а не новым коммитом.
